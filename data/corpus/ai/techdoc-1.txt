The security of a networked application is bounded by the age of the machinery underneath it. As of 2014, the TLS and SSL support in the Python 2.7 standard library is roughly four years old, settled when 2.7.0 was prepared in 2010, and the corresponding support in Python 2.6 has been frozen for six. Under ordinary circumstances this would be unremarkable. A maintenance branch exists precisely so that it does not move underneath the people who depend on it. Network security is not an ordinary circumstance. In the interval since 2.7.0, protocol versions in common use have been deprecated, cipher suites once considered adequate have been broken or abandoned, certificate verification practices that were formerly a matter of local taste have become the baseline expectation of every other major platform, and the published evidence has made it clear that persistent, indiscriminate interception of internet traffic is considerably more widespread than the threat models of the preceding decade assumed. The standard library did not become less correct during those four years; the world around it moved, and the distance between the two is now large enough to be a defect in its own right.

The practical consequence is that a program written against the network security facilities of Python 2.7 as shipped cannot responsibly be recommended for use on the public internet. That is an uncomfortable thing to write about the version of Python most people are actually running. Nor is it a statement documentation can repair: the missing capabilities are not conveniences a careful author could write for himself in application code, but properties of the protocol implementation and of the primitives beneath it.

Part of the gap is covered on Linux and the BSDs, where Python links against the operating system's OpenSSL and the vendors of those systems patch it diligently. This is a genuine mitigation, but only a partial one. Linking against a modern OpenSSL means that an application inherits whatever defaults the vendor chose; it does not give the application any way to ask for something stronger, or to refuse something weaker, because the standard library exposes no interface through which the request could be made. An application that wishes to insist on a particular protocol version, restrict the cipher list, or verify that the certificate presented actually corresponds to the host it dialled has no supported means of doing so. The usual answer to this has been to direct users toward third-party cryptographic and HTTP libraries, and those libraries are good ones. But that answer imposes a deployment burden that many environments cannot absorb, requires a build toolchain where none was needed before, and, most importantly, depends on the user already knowing that the third-party library exists and why it is necessary. A default that is unsafe unless the user has read the right blog post is not a defensible default.

On the Windows and macOS installers the situation is different in a way that indicts us more directly, because there the core team chooses which OpenSSL is bundled. Our practice has been to confine ourselves to OpenSSL maintenance releases within whatever series was current when the Python feature release was made. We have, in other words, held a lever we declined to pull.

The specific omissions can be named. Server Name Indication is absent, so a client cannot reach a virtual host on a shared address correctly and a server cannot select among several certificates. Certificate hostname matching is not available, which reduces certificate verification to a check that some valid certificate exists somewhere in the world. There is no constant-time comparison primitive, so every application that compares a MAC or a token does so with an operator whose running time depends on the data. There is no standard password hashing function, with the result that the obvious thing to reach for is a bare cryptographic hash. And there is no way to ask the hash module which algorithms it actually has, so code that would prefer a modern digest and fall back gracefully cannot discover what is available. Alongside these sits the operating system's randomness interface, whose reliable behaviour underpins all of them.

The deeper argument is about the shape of the branch rather than any individual feature. Python 2.7 is the only genuinely long-term maintenance branch this project has ever had, and it will be supported for something close to a decade. Policies calibrated for an eighteen-month or even a five-year window stop producing their intended effect over that span. Feature freeze exists to protect users from churn, but stretched across ten years the guarantee inverts: an unchanging security module does not preserve the user's position, it steadily erodes it, since the threat environment is not bound by our release policy. Keeping security-relevant modules genuinely maintained over such a period requires permission to add features, while holding existing interfaces stable and behaviour compatible.

There is precedent for this outside our own project. Enterprise Linux distributions attach their support commitments to a whole point-release series rather than to the first release of that series, and they ship security functionality, not merely security patches, in those point releases, under strict backwards-compatibility guarantees that redistributors and their customers have learned to rely on. The model is well understood.

The selection rule proposed here follows from that reasoning. A missing feature qualifies for backporting only when its absence has security consequences beyond the individual Python program and the machine it runs on. Network protocol support qualifies, because a weak connection endangers the peer and everyone whose traffic crosses the same path. Password storage qualifies, because a breach propagates to every other service where the credential was reused. Operating-system randomness qualifies, because everything else rests on it. A faster parser or a friendlier exception does not. The line matters: the point is to keep maintenance releases safe to apply on sight, and nothing would undermine this proposal faster than teaching users to approach a 2.7.x update with the same wariness they reserve for a feature release.
