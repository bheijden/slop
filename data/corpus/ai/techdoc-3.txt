The first thing to settle is which interface is under discussion, because two very different promises are routinely confused. The interface the kernel presents to userspace, the system calls and the behaviour surrounding them, is stable and is meant to stay that way. Programs built against it fifteen or twenty years ago are still expected to run today, and a change that breaks them is treated as a bug in the kernel rather than as an unfortunate consequence of progress. The interfaces inside the kernel, between one subsystem and another and between a subsystem and a driver, carry no such promise. They change whenever changing them produces a better kernel, and there is no version of the kernel in which they will stop doing so. This is a deliberate design decision, not an oversight, and it is worth explaining why.

Begin with what the driver author actually wants, which is almost never what is asked for. The request is usually phrased as a demand for a frozen interface. The underlying desire is for a driver that keeps working, on the kernels users will actually run, without the author having to chase every release. Those are not the same thing, and the kernel has a better answer to the second: get the driver merged into the mainline tree. Everything that follows is an argument for why that answer is the practical one and why the alternative is not available even in principle.

Set aside the legal questions about non-GPL and binary-only modules. They are real, and they have been argued at length elsewhere. The argument here is purely technical, and it holds regardless of how the legal one is resolved.

A stable binary interface cannot be provided because the binary layout of the kernel is not a property of the source alone. The compiler affects it: different compiler versions lay out structures with different alignment and padding, and make different decisions about which functions are inlined, so a module built with one compiler may be subtly and silently incompatible with a kernel built by another. The build configuration affects it more dramatically still. Configuration options determine which fields a structure contains, so the same structure has different sizes and different member offsets in two kernels built from identical source; some options determine whether a given function exists in the kernel at all. And the kernel runs on a great many processor architectures, each with its own calling conventions, alignment rules and word sizes. A binary blob is a snapshot of one point in a large space, and it is only valid at that point.

It is true that a module compiled against one exact configuration, with one compiler, for one architecture, will load and run. That is how vendor modules for a single distribution release are produced. The trouble is arithmetic. Count the distributions, then the releases each supports concurrently, then the kernel variants shipped within a single one of those releases: builds tuned for particular processor families, for large memory configurations, for virtualisation, for debugging, for real-time behaviour. Multiply. The result is a build matrix that nobody has ever succeeded in maintaining, and each entry in it must be rebuilt and retested when any of its inputs changes. Providing one binary is easy; providing all the binaries that users will need is a treadmill that gets faster every year.

The internal source interfaces are not frozen either, and for a related reason: kernel development does not stop. When developers find a bug in an interface, or discover a design that is simpler, faster, or harder to misuse, they change it. Functions get renamed, structures get reorganised, parameters get added, removed or reordered. Crucially, the same patch that changes an interface also updates every caller of it in the tree, so the change lands complete rather than leaving a period during which some callers are broken. That is only possible because the callers are in the tree.

The USB subsystem is the standard example. Its internal interfaces have been reworked at least three times over the years. One of those reworkings moved data handling from a synchronous model to an asynchronous one, which substantially increased throughput for every USB device in the system. Another changed how packets were allocated and resolved a set of documented deadlocks. Neither improvement could have been made behind a fixed interface. Closed systems that did preserve their old USB interfaces were obliged to carry the previous, inferior mechanisms forward alongside the new ones, which left obsolete and error-prone paths sitting in the documentation where new developers would find them and use them.

Security is the sharpest form of the same argument. A great many security fixes are not one-line corrections to a single driver; they require reworking an internal interface so that the dangerous usage becomes impossible rather than merely discouraged, or so that a check happens in one place instead of in each of forty callers. Being able to fix every caller in the same change is what prevents the flaw from quietly reappearing in the next driver written by someone who copied the old pattern. For the same reason, interfaces that no longer have users are deleted rather than kept for old times' sake; unused code must still be maintained and audited, and the kernel is expected to run on machines where its size genuinely matters.

The conclusion is a practical one. Write the driver under a GPL-compatible licence, submit it, and get it into the mainline tree. From then on, when someone changes an interface the driver uses, it is that person's responsibility to update the driver, and they will, because the tree must build. The driver will be present in every distribution kernel without any packaging effort on your part. Other people will fix its bugs, port it to architectures you do not own, and add features you had not planned. That is a considerably better deal than a stable interface, and unlike a stable interface it is actually on offer.
