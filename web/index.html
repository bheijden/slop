slop.

A linter for prose.

Flags stock LLM phrasing: it is important to note that, no X, no Y, no Z, at the line it came from, with the fix. Nothing leaves your browser.

    What the two phases checkconformance and fudging

    Conformance runs every example you wrote. Each tests.hit must match, and each tests.miss must not. That is what catches the very rule below, whose pattern has no word boundaries and so fires on "Every request".

    Fudging then rewrites each hit 27 ways with the markup real files carry, and requires the rule to still fire:

    **It is important to note that** this works.   md:bold-span
It is imp**ort**ant to note that this works.   md:bold-inside-word
It is important\nto note that this works.      md:soft-wrap
<p>It is imp<b>ort</b>ant to note that …       html:tag-inside-word

    A rule that passes a clean sentence but fails a marked-up one will miss things in real files. Soft-wrapped markdown is the usual culprit (a sentence broken across two lines at column 80 stops matching) and nothing tells you.

    The rule formateight kinds

    regex covers most rules. The other seven count things a regex cannot express, such as repeated sentence shapes or a rate across a whole document. All eight, with their parameters, are in the rule format reference.

    Wrap your rules in a set and the file is shareable as it is: { "name": "house-style", "version": "0.1.0", "rules": [ … ] }.

    Using your rules for realpage, URL or CLI

    Three ways in, all the same file:

    drop the .json on the check page               # or use its rules panel
?rules=https://example.com/house-style.json    # fetched, then run here
slop check --rules house-style.json docs/ -r   # command line

    Passing tests means a rule does what you wrote. It does not mean the rule is worth having. For that, run it over prose you did not write it against and read the hits:

    slop check --rules mine.json --select mine ~/writing -r

    A rule firing on a lot of good prose is a rule to tighten, whatever its examples say. Two worked examples, one tightened and one kept with its false firing documented, are in calibration and the rule audit.

    Command linefor agents and CI 
    # one-off, nothing installed
npx --yes github:bheijden/slop check docs/ -r

# repeated use: npx re-resolves the repo each call (~5s), a clone runs in ~0.2s
git clone --depth 1 https://github.com/bheijden/slop
node slop/js/cli.mjs check docs/ -r

node slop/js/cli.mjs check --format json docs/ -r   # match, sentence, why, suggest
node slop/js/cli.mjs check --select wikipedia-ai .  # a set name or one rule id
node slop/js/cli.mjs check --share -r docs/        # a link to this page

    No dependencies; the clone is 380 KB and needs only Node. Same engine and rule files as this page.

    Findings never fail a run on their own. They are style smells, not errors. Add --max-per-1000 2 or --max 0 when you want CI to gate on them. Exit 0 ok, 1 over a budget you set, 2 usage or read error.

    Install as an agent skillSKILL.md

    A SKILL.md ships with the repo, so a coding agent runs this by itself whenever it is writing or editing prose for you. Copy it into your skills directory:

    D=~/.claude/skills/linting-prose        # or .claude/skills/… for one project
R=https://raw.githubusercontent.com/bheijden/slop/main/skill

mkdir -p $D/reference
curl -sL $R/SKILL.md -o $D/SKILL.md
for f in rules authoring; do curl -sL $R/reference/$f.md -o $D/reference/$f.md; done

    Or hand the instruction to the agent and let it install itself:

    Install the slop skill from
github.com/bheijden/slop/tree/main/skill into
~/.claude/skills/linting-prose/, keeping the reference/ files.

    Only the name and description sit in context until the skill is triggered, so it costs about 100 tokens to have installed. The body loads when the agent is actually editing prose, and reference/rules.md and reference/authoring.md only when it needs the rule catalogue or is writing a rule.

    A skill gives an agent instructions it will act on, so read one before installing it. This one runs npx or a clone of this repo and nothing else. See Anthropic's Agent Skills docs.

    Update an earlier installthe rule format changed

    Hand this to your agent:

    Update my slop install from github.com/bheijden/slop.
Pull the clone if I have one, and re-copy skill/SKILL.md and
skill/reference/*.md over ~/.claude/skills/linting-prose/.
The rule format changed: a rule now carries "match" (what it
finds) and "notable" (when that is worth reporting) instead of
top-level "kind" and "params". If I have my own rule sets under
.slop/rules/, migrate them and run: slop test-rules <file>

    Or by hand:

    # the clone
git -C slop pull --ff-only

# the skill: the same commands as installing, -o overwrites
D=~/.claude/skills/linting-prose
R=https://raw.githubusercontent.com/bheijden/slop/main/skill
curl -sL $R/SKILL.md -o $D/SKILL.md
for f in rules authoring; do curl -sL $R/reference/$f.md -o $D/reference/$f.md; done

    npx needs nothing. It re-resolves the repo on every call, so it is already current.

    Your own rule sets need editing. kind and params move inside match, and notable says when a count is worth reporting: { ">": 0 } for a rule that fires on any occurrence. Loading an old set names the rule and what to change. The rule format has the rest.
